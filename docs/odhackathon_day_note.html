1. 背景・前提

前回ハッカソンは3人。今回は自分を含め2人が加わり、5人体制になる想定。 自分は前回参加していないので、まず「既存実装を壊さず理解する」ことが重要。

プロダクトの将来像として出ている5項目

  1. 個人が自身の精神状態を管理・把握するための補助
  2. 利用者のエリアごとの気分の可視化
  3. エリア・イベント・季節・事故・天気など、事象に合わせた気分変動の把握・予測
  4. 蓄積データによる、個人に合わせた気分予報と簡単な改善案の提示
  5. 蓄積データによる、エリア等の集団の気分傾向の把握・提示
重要な理解 前回は③の途中、「天気 × 気分」の関連付けまで進んでいる。 したがって今回は新規アプリを作るのではなく、v1をv2へ拡張するイメージ。
今回の大会で追加される重要条件 今回は都知事杯オープンデータハッカソン。 したがって「既存アプリにオープンデータを載せる」のではなく、 オープンデータが分析・予報・提案のどれかを実際に変える設計にしたい。

3. 今回の狙い

機能を増やすより、「ユーザーに何が新しく分かるか」を主語にする。

プロダクト原則 ユーザーが気分を記録するたびに、「記録して終わり」ではなく、 自分について何か1つ新しく分かること。

今回の価値

① 自分の傾向が分かる

「雨の日は低め」「金曜日は高め」「最近下降傾向」など。

② 明日の予報が出る

本人の履歴と明日の条件から、予想気分スコアを表示。

③ なぜその予報か分かる

ブラックボックスにせず、予測要因と寄与を表示。

④ 自分に合った小さな提案

一般論ではなく、「過去の自分のデータ」から改善案を出す。

今回の主役にしないもの

集団の高度分析

地域・属性・イベントごとの長期傾向は将来価値として見せる。

事故・ニュースの本格連携

取得・分類・地域紐付け・因果解釈が重い。今回のMVPでは避ける。

4. オープンデータ戦略

都知事杯ではここが企画の芯。オープンデータを「添える」のではなく、 本人の気分データだけでは分からない“街側の文脈”を与える材料として使う。

基本コンセプト 本人が記録する「気分」と、都市が公開する「その日・その場所の状況」を掛け合わせる。
Personal Mood Data × Urban Open Data → お元気予報

オープンデータを使う目的

① 気分の背景を知る

天候・大気・イベント・季節など、「本人の内側」だけではない条件を特徴量にする。

② 個人予報を豊かにする

「雨の日」「イベントのある日」「大気状況が違う日」など、本人固有の傾向を探す。

③ 街の傾向へ広げる

十分な匿名データが蓄積したら、エリア単位の長期傾向も分析可能にする。

最重要ルール：オープンデータを“飾り”にしない

弱い使い方 「東京都には公園が○件あります」「イベント情報を別画面に一覧表示します」だけでは、 お元気予報の価値と接続しない。
強い使い方 オープンデータの値が、傾向分析・予報・理由表示・改善提案のどれかに直接影響する状態にする。 「このデータを外すと結果が変わる」が目安。

候補データと優先順位

「リアルタイムかどうか」だけではなく、何のために使うデータかで整理する。 お元気予報では、未来を予報する / 今を解釈する / 行動につなげる / 集団傾向を見るの4役に分けると考えやすい。

のように、「予測材料」と「その後の行動・地域体験」まで接続させる。

既存の天気データとの位置づけ

Open-Meteoによる天気連携は既存資産として残す。ただし今回の都知事杯では、 東京都・自治体が公開するオープンデータも別に1種類以上、主要ロジックへ組み込む方針が分かりやすい。

PM2.5の扱いは「未来予報」ではなく「現在・過去分析」寄り 速報値が取れても、翌日の予測値が取れないなら「明日のお元気予報」の主特徴にはしにくい。 過去データから本人傾向を見つけたり、今日の状態を解釈したりする用途で使う。

5. 機能要件

P0を全部終えるまではP1・P2に手を出さない。

優先度 機能 内容 完成イメージ
P0 個人傾向分析 天気・曜日・直近トレンド等と本人の気分の関係を計算。 「雨の日 -0.6」「金曜 +0.3」
P0 明日の気分予報 明日の条件と本人履歴から予測値を算出。 「明日は 3.7 / 5」
P0 予測理由表示 予測に効いた要素をユーザーに見せる。 「晴れ +0.4 / 金曜 +0.3」
P0 信頼度表示 データ件数・条件一致件数から予報の確からしさを表現。 低 / 中 / 高
P0 東京都オープンデータ統合 イベントまたは大気環境など最低1種類を、傾向分析・予報・理由のいずれかへ直接利用。 「ODを外すと結果が変わる」状態
P1 改善提案 本人の過去行動と気分の関係から軽い提案。 「散歩した日は +0.4」
P1 行動タグ 散歩・運動・残業・飲酒など、分析に使える軽量タグ。 投稿時に数タップ
P2 イベント連携 地域イベント等との関連を試験的に表示。 将来展望でも可
P2 集団傾向分析 地域・季節などの匿名集団傾向を長期分析。 将来展望

ユーザーフロー

気分を投稿→ 履歴が蓄積→ 個人傾向を発見→ 明日の気分予報→ 根拠を見る→ 軽い提案

6. 気分予報ロジック

ハッカソンでは「高度なML」より、説明可能でデモしやすいロジックを優先。

🌤
3.7 / 5
明日のあなたの気分予報

やや晴れ。最近の傾向と明日の条件から、今日より少し持ち直す予想。

☀️ 晴れの日+0.4
📅 金曜日+0.3
📉 直近7日トレンド-0.2
📊 データ量28件

最小実装の考え方

baseline = 直近7日または14日の本人平均

weather_adjustment
  = 同じ天気の日の本人平均 - 本人全体平均

weekday_adjustment
  = 対象曜日の本人平均 - 本人全体平均

trend_adjustment
  = 最近の上昇 / 下降傾向を小さく補正

open_data_adjustment
  = 採用した東京都ODの該当条件における本人平均との差
    例: イベント開催日 / PM2.5帯など

forecast
  = baseline
  + weather_adjustment
  + weekday_adjustment
  + trend_adjustment
  + open_data_adjustment

forecast = 1.0〜5.0 に clamp
重要 「3.7」という値をAIに作らせない。数値はコードで計算し、AIは説明文の生成だけに使う。

将来的な発展

  • 温度帯、気圧、湿度、季節、時間帯
  • 行動タグ（運動、散歩、残業、飲酒、友人との交流等）
  • 単純回帰 / 決定木 / 時系列モデルなどへの置き換え
  • ただし「説明可能性」は残す

7. コールドスタート

新規ユーザーはデータがない。ここを無視すると「予報アプリ」として破綻する。

記録数 表示 意味
0〜2件 「記録をためています」 地域の気分・今日の振り返りを中心に見せる
3〜6件 「少し傾向が見えてきました」 単純な曜日・天気傾向を限定表示
7〜19件 簡易予報 信頼度は低〜中として表示
20件以上 個人予報 複数要因＋理由表示
デモでは 過去30日程度の「デモユーザー」をシードしておく。リアルに当日投稿を積み上げて予報を成立させようとしない。

8. AIの責務

AIにやらせる

数値結果の文章化／予測理由のやさしい説明／ 医療的でない軽い提案文／将来的には自由記述のタグ化。

AIにやらせない

予測スコアそのもの／統計計算／地域集計／診断／ 「あなたは○○状態です」の断定。 

投稿・外部データ
      ↓
統計 / 予測ロジック
      ↓
forecast = 3.7
reasons = [晴れ +0.4, 金曜 +0.3, trend -0.2]
      ↓
LLM
      ↓
「明日は比較的気分が上向きやすい条件です」
「ChatGPTでよくない？」への答え LLMに気分を当ててもらうサービスではなく、本人が蓄積した時系列データを分析し、 その人自身の傾向を予報に変えるサービス。LLMは伝達レイヤー。

9. プライバシー・表現

気分 + 位置情報はセンシティブ。MVPでも最低限の設計原則を守る。

位置情報

現在地はエリア判定にのみ使用。緯度経度はDBに保存しない既存方針を継続。

匿名性

ログインなしの匿名ID。地域集計は一定件数未満なら非表示。

診断しない

「うつ」「躁」などの診断・断定表現は避け、あくまで本人の気分記録として扱う。

因果を断定しない

「雨のせいで悪化した」ではなく「雨の日に低い傾向がある」と表現。

言葉の注意 「精神状態予測」「メンタル変動予測」は強すぎる可能性がある。 発表では「気分傾向」「気分予報」「関連が見える」を中心にすると安全。

14. デモ案

技術紹介ではなく、ユーザーの体験として一本で見せる。

おすすめデモストーリー

  1. アプリを開く。東京23区の「今の気分」が見える。
  2. 「これは前回作った、街の気分を見る機能です」と10秒で説明。
  3. マイページへ移動し、過去の自分の気分履歴を見せる。
  4. 「今回は、この記録を未来に使います」と転換。
  5. 「あなたは雨の日に -0.6、金曜に +0.3」の傾向を表示。
  6. 東京都・自治体のオープンデータから、明日の都市条件を表示（例：イベント予定 / WBGT）。
  7. 明日の条件を使い「お元気予報 3.7 / 5」を表示。
  8. なぜ3.7なのか、天気・曜日・オープンデータ由来の要因と信頼度を表示。
  9. 本人の傾向に応じて「散歩した日は +0.4」などを表示。
  10. 余裕があれば、公園・クーリングシェルター・スポーツ施設等のODから具体的な行動候補を1つ提示。
発表の対比 前回：「今の街を見る」
今回：「自分の明日を予報する」

説明の一言候補

「天気予報は空の状態を予報します。
お元気予報は、自分自身の記録と、
街が公開しているオープンデータを掛け合わせて、
“自分の気分の予報”を育てていきます。」

15. リスクと逃げ道

リスク問題逃げ道
データ不足 個人予報が成立しない デモユーザーに30日分のシード
AIが落ちる 文章生成でデモ停止 数値・理由はコードで生成し、定型文fallback
機能を広げすぎる イベント・事故・ニュース連携で時間消費 天気 + 曜日 + trendまででP0成立
予測が怪しく見える 「AIが適当に言っている？」 理由・データ数・confidence表示
UIが間に合わない 凝った予報画面で詰まる 既存マイページに予報カード1枚追加
既存コード把握に時間 新規参加2人が動けない 30分でRepoツアー、I/Fを切って独立作業
ODの粒度・形式が合わない 区・日時でJoinできず、ETLだけで時間を消費 開始時にサンプルを確認。Join可能性を見て1種類に即決
時間軸が用途と合わない 実測値しかないデータを「明日予報」に無理に使ってしまう Historical / Current / Future のどれに使うデータか最初に分類
ODが飾りになる 大会テーマとの接続が弱く見える 予測理由または分析結果へ必ず直接効かせる
やらない勇気 P0が完成していない状態で、事故・ニュース・属性分析・本格ML・SNS機能には手を出さない。
